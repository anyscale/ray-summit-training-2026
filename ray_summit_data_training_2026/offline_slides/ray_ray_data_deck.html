What is Ray?

  • OSS framework for high-performance, resilient, scale-out computation on heterogeneous hardware.
  • Distributed scheduler for stateless functions (tasks) and long-running stateful processes (actors).
  • Key features:
    • Dependency tracking — task graphs
    • Data-movement & resource aware
    • Mixed resources: GPUs, fractional & custom
  • Infra: distributed object store, fault tolerance via GCS.
  • Easy, Python-first APIs and patterns.

End-to-end demo — load & process data with Ray Data

Product-category prediction. Start by reading the catalog and cleaning text. A per-row transform uses map().

ds = ray.data.read_csv(".../ecommerce_product_catalog.csv")

# lowercase, strip punctuation, concat title + description -> "text"
ds_cleaned = ds.map(clean_and_combine)
ds_cleaned.take(5)

Datasets are lazy & streaming: each operator returns a new Dataset; nothing executes until you take/write the data.

Vectorize & encode with map_batches

A stateful, batch transform (fitted vectorizer + label map) runs in parallel across block partitions via a class actor.

# stateful batch transform -> runs as an actor pool
ds_encoded = ds_cleaned.map_batches(VectorizeAndEncode)

# split for training
train_ds, val_ds = ds_encoded.train_test_split(test_size=0.2, seed=42)
print(train_ds.count(), val_ds.count())

Batch inference & online serving

Offline — Ray Data

Model is the reusable actor state.

class OfflinePredictor:
    def __init__(self):
        self._model = ProductClassifier()
        self._model.load_state_dict(
            torch.load(best_path + "/model.pt"))

    def __call__(self, batch: dict) -> dict:
        with torch.inference_mode():
            o = self._model(
                torch.tensor(batch["features"]))
        return {"prediction": o.numpy()}

preds = val_ds.map_batches(
    OfflinePredictor, concurrency=2)

Online — Ray Serve

A class becomes an HTTP deployment.

@serve.deployment
class OnlinePredictor:
    def __init__(self, checkpoint):
        self._model = ProductClassifier()
        self._model.load_state_dict(
            torch.load(checkpoint))

    async def __call__(self, request):
        data = json.loads(await request.json())
        return {"prediction": self.predict(data)}

handle = serve.run(
    OnlinePredictor.bind(checkpoint=ckpt))

A brief look at Ray Core — tasks

Any Python function you can write, you can distribute. Decorate it, then schedule it with .remote().

@ray.remote(num_cpus=2)
def f(a, b):
    return a + b

ref = f.remote(1, 2)   # returns immediately
ref                    # -> ObjectRef(...)

ray.get(ref)           # block & fetch -> 3

ObjectRef = a handle to a (maybe not-yet-computed) result. We don't block until we call ray.get.

Task graphs & actors

Task graphs

Pass ObjectRefs as args — Ray resolves dependencies and schedules without blocking.

arg1 = add.remote(1, 2)
arg2 = add.remote(10, 20)
out  = add.remote(arg1, arg2)   # depends on both
ray.get(out)                    # -> 33

Actors — stateful

Long-lived class instances in the cluster. Common use: load a large model once and route calls to it.

@ray.remote
class Accounting:
    def __init__(self):  self.total = 0
    def add(self, amt):  self.total += amt
    def total(self):     return self.total

acc = Accounting.remote()
acc.add.remote(100)
ray.get(acc.total.remote())   # -> 100

Storage scopes on Anyscale — shared_storage (org), cluster_storage (cluster), per-user & fast local — give best-practice data placement. As of 2026 Ray Data has a query optimizer + planner (logical & physical optimizations).

The core pattern: map_batches + an actor

Batch inference (here: text embeddings for semantic search). Constructor holds the heavy state (the model); __call__ transforms a batch.

class AddEmbedding:
    def __init__(self, model_id):
        self.model = SentenceTransformer(model_id)

    def __call__(self, batch, source, dest):
        batch[dest] = self.model.encode(batch[source])
        return batch

ds.map_batches(
    AddEmbedding,
    compute=ray.data.ActorPoolStrategy(size=2),   # pool of model actors
    fn_constructor_args=[model_path],             # -> __init__
    fn_args=["desc", "desc_emb"],                 # -> __call__
)

Performance: blocks, parallelism & GPUs

  • Ray Data streams data as blocks (~100 MB–1 GB), sized automatically — independent of your batch size.
  • One block → one actor. A small dataset = one block = no parallelism.
  • repartition(n) splits into more blocks → more parallel actors. (1.5 min → much faster.)
  • materialize() caches blocks in the object store for fast iterative testing.
  • GPUs aren't autoscaled — set an explicit compute strategy.
ray.data.read_parquet(src) \
  .repartition(4) \
  .map_batches(
     AddEmbedding,
     num_gpus=1,           # schedule on GPU
     batch_size=64,        # fit GPU RAM
     compute=ray.data.ActorPoolStrategy(size=2),
     fn_constructor_args=[model_path],
     fn_args=["desc", "desc_emb"],
  ).write_parquet(dest)
# GPU run: ~10s  (vs ~90s CPU, 1 actor)

Tip: if a pipeline is interrupted, stray actors may hold resources — ray.shutdown() resets cleanly.

Scaling LLM inference with RayLLM + vLLM

Generate multimodal catalog copy (image + text → text). Same map_batches idea, but a managed vLLM engine replaces the hand-written actor — faster and simpler.

config = vLLMEngineProcessorConfig(
    model_source=model_path,
    engine_kwargs=dict(max_model_len=8192,
                       limit_mm_per_prompt={"image": 1}),
    batch_size=8, concurrency=2,        # ~= GPUs used
)
processor = build_llm_processor(
    config,
    preprocess=lambda row: dict(messages=[...], sampling_params=...),
    postprocess=lambda row: dict(cat_desc=row["generated_text"], ...),
)
ds = processor(ray.data.read_parquet(src))
