The model: a two-tower recommender

class TwoTower(nn.Module):
    def __init__(self, n_users, n_items, dim=64):
        self.user_emb = nn.Embedding(n_users, dim)
        self.item_emb = nn.Embedding(n_items, dim)

    def encode_users(self, uid):
        u = self.user_emb(uid)
        return F.normalize(u, dim=-1)

    def encode_items(self, iid):
        v = self.item_emb(iid)
        return F.normalize(v, dim=-1)

    def forward(self, uid, pos_iid):
        u = self.encode_users(uid)      # [B,D]
        v = self.encode_items(pos_iid)  # [B,D]
        return u @ v.t()                # [B,B]

Each tower maps an id to a normalized vector; recommendation = find items whose vectors are most similar to the user's. Top-k by score gives the recommendations.

Each step is an independent, testable transform. Stateless steps use plain functions; steps that hold state (the model, a queue client) use a class that Ray runs as an actor.

Why a pipeline? Datasets are lazy & streaming — build and test step-by-step on a small sample, then run the whole thing at scale without changing the code.
Real systems read users & products from databases. We front that with a named Ray actor as a database facade — looked up by name anywhere in the pipeline.

Reading data — and a real gotcha

Ray Data reads many formats, but defaults can surprise you. Troubleshoot by comparing against PyArrow / Pandas.

# JSON lines read returns NO rows... no error, no data!
ds = ray.data.read_json('.../users.ndjson', lines=True)
ds.materialize()                       # -> 0 rows

# PyArrow & Pandas read it fine -> data & libs are OK
# Cause: Ray Data filters to *.json by default, skipping .ndjson
ds = ray.data.read_json('.../users.ndjson', lines=True,
                        file_extensions=['.ndjson'])   # fixed

materialize() caches the dataset in the object store — ideal for inspecting and iterating on small data while developing. Lesson: when results look wrong, isolate Ray Data from your data and other libraries.

A named actor as a service facade

Define & name the actor

@ray.remote
class DatabaseFacade:
    def __init__(self, users, products):
        self.users = pd.read_json(users, lines=True)
        self.products = pd.read_parquet(products)
    def users_for_ids(self, ids):
        return self.users[self.users['id'].isin(ids)]
    def products_for_indices(self, idxs):
        return self.products.iloc[idxs]

# create once, register a name
DatabaseFacade.options(name="database") \

def get_user_indices(batch):
    db = ray.get_actor("database")     # by name
    ref = db.users_for_ids.remote(batch['id'])
    batch['user_index'] = ray.get(ref).index.values
    return batch

ds.map_batches(get_user_indices)

The actor holds state (loaded tables); pipeline functions stay stateless and just call it. Remote calls return ObjectRefs; ray.get fetches the value.

The model step: a stateful map_batches actor

The recommender loads the model once in __init__; __call__ scores a batch of users and attaches top-k items. No @ray.remote needed — Ray makes it an actor.

class Recommend:
    def __init__(self, model_location, num_recommendations, num_users, num_items):
        self.model = TwoTower(num_users, num_items)
        self.model.load_state_dict(torch.load(model_location, weights_only=True))
        self.model.eval()
        self.num_recommendations = num_recommendations

    def __call__(self, batch, column):                 # column = "user_index"
        batch['recommended_items'] = self.recommend_for_users(batch[column])
        return batch

ds.map_batches(get_user_indices) \
  .map_batches(Recommend, fn_constructor_args=[model_path, 3, 1000, 1000],
               fn_args=['user_index'])

Finish the pipeline — emails, queue & blocks

# per-row email text -> use map()
def generate_email_for_user(user):
    user['reco_email'] = render(user)
    return user

# stateful queue adapter -> map_batches (an actor)
class EmailSendingQueue:
    def __init__(self, service_info):
        self.queue = {'service': service_info, 'out': []}
    def __call__(self, batch):
        self.queue['out'] += list(batch['reco_email'])
        batch['queued'] = [True]*len(batch['reco_email'])
        return batch

Gotcha: blocks vs. batches

Asking for a small take_batch(2) still processed all 1000 records — because the tiny dataset is a single block, and Ray Data must process a whole block at a time.

repartition(n) creates more blocks, so a small take touches fewer records. This matters a lot when each inference is slow/expensive (e.g. an LLM) during iterative development.

map = per row  |  map_batches = per batch + reusable actor state. Side effects (sending mail) become a column marking what was queued.

Online serving with Ray Serve

Start simple: one deployment handling request I/O (ingress) and recommendation logic. Decorate a class, bind it, run it.

@serve.deployment
class IngressAndRecommender:
    def __init__(self, base_model_path, num_recos, num_users, num_products):
        self.db = ray.get_actor("database")
        self.recommender = Recommend(base_model_path, num_recos, num_users, num_products)

    async def __call__(self, request: Request):           # HTTP entrypoint
        user = json.loads(await request.json())

Semantic search as a deployment

Reuse the Part-1 description embeddings: encode the query, rank by vector similarity, then rerank by name string-distance.

@serve.deployment
class SemanticSearch:
    async def __init__(self, model, db):
        self.model = SentenceTransformer(model)
        self.db = db
        all_p = await self.db.all_products.remote()
        self.embs = all_p['desc_emb']

    async def search(self, query, matches):
        sims = self.model.similarity(
            self.model.encode(query), self.embs)
        top = sims.flatten().topk(50).indices
        products = await \
            self.db.products_for_indices.remote(top)
        # rerank by name similarity
        best = torch.tensor([lcsstr(query, n)
            for n in products['name']]).topk(matches).indices
        return products.iloc[best]

Per-deployment control

  • num_replicas — fixed parallelism for a component.
  • autoscaling_config — min/max replicas that scale with load.
  • ray_actor_options — CPUs and fractional GPUs (e.g. num_gpus: 0.5 packs two replicas per GPU).
  • Health-check & graceful-shutdown timeouts per deployment.

Watch out for runtime details: working dir, imported modules, env vars, and name scoping — Python wasn't designed for a distributed runtime, so be explicit.
